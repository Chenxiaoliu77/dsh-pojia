## 6 扩展维护性规划

### 6.1 模块化设计与架构弹性

**分层与依赖方向（单向，禁止回指）**

| 层 | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|
| **L0 installer** | 唯一有写盘权；必须能独立运行（用于修复已坏掉的 L1） | 标准库 | 依赖 L1–L4 |
| **L1 core** | 计划器 / 执行器 / 记忆 / 注册表 / 守卫 / 自检 | L0 | 依赖 L2–L4 |
| **L2 modules** | A / B / C′ / D′ / E 五个业务模块 | L0, L1 | 依赖 L3, L4；**禁止直接 import 宿主 ctx** |
| **L3 adapters** | 进程内适配器 + MCP 适配器 | L0–L2 | 被 L2 反向依赖 |
| **L4 ui** | 前端 | L0–L3 的公开接口 | 直连数据层 |

**为什么 adapter 必须在 modules 之上**：同一份模块代码要以两种平面挂出去。模块若直接依赖宿主 ctx，就锁死在进程内，MCP 平面无法复用。

**新增一个模块的改动面 = 2 个文件**

| 要改的文件 | 内容 |
|---|---|
| `modules/<X>/capabilities.json` | 能力声明（名称、权限档、输入输出 schema 引用） |
| `modules/<X>/SKILL.md` | 模型侧说明（name 必须匹配 ^[a-z0-9]+(-[a-z0-9]+)*$） |

其余由目录扫描派生。**若某天需要改第 3 个文件，说明架构退化了**——这是硬判据。

**四个横向延伸点（都不用改中心）**

| 延伸点 | 加什么 | 影响面 |
|---|---|---|
| 新平面 | 新增一个 adapter | 只动 L3 |
| 新权限档 | 在 P0/P1/P2 之上插入 | 只动 L1 的权限判定 + 一处映射 |
| 新记忆层 | 在会话/项目/全局之外加一层 | 只动 L1 的存储接口 |
| 新网络对象类型 | 加一条分类规则 + 一段输出 schema | 只动 L2 的一个模块 |

### 6.2 可扩展性评估

| 维度 | 现状 | 目标 | 分数（0–5） | 依据 |

### 6.6 文档完整性与知识传承机制

**文档四级分层**

| 级 | 类型 | 当前文件 | 读者 | 更新触发 |
|---|---|---|---|---|
| **L1 主报告** | 结论性长文，四部分结构 | `docs/破甲机制研究报告.md` | 想一次读懂全貌的人 | 结论被推翻时 |
| **L2 专题** | 单一主题深挖 | 宿主防御 / 生态全景 / 提示词调研 / 桌面助手方案 / 集成规范 / 计划表 | 需要某一面细节的人 | 对应领域有实测更新 |
| **L3 操作** | 可复制命令与步骤 | 各文档内的「复现路径」节 | 要动手的人 | 命令失效时 |
| **L4 决策** | ADR，一条一个决定 | `docs/adr/NNNN-*.md`（首批 3 条随 T-39 建立） | 想知道「为什么这么定」的人 | 做出不可逆决定时 |

**三条传承机制**

1. **决策留痕**：任何不可逆决定（选型、契约冻结、放弃某方向）必须写 ADR，格式固定为「背景 / 选项 / 决定 / 后果」。**没有 ADR 的变更在评审时可被直接驳回。**
2. **术语统一**：根 `GLOSSARY.md` 一个词条一句话，只收「本项目特有且容易误解」的词（如破甲、平面、P 档、三段输出、灵魂闸门）。**同一概念全文只准一种写法。**
3. **口径唯一实现**：同一计算（如评分、分类、去重）在代码里只能有一处实现，其他地方调用它。该原则来自对上游的实测观察——同一口径写三遍必然漂移成三种。

**新人 30 分钟上手路径**

| 步 | 读什么 | 用时 |
|---|---|---|
| 1 | README 的「这个仓库是什么」+ 核心结论速览 | 5 分钟 |
| 2 | `GLOSSARY.md` | 3 分钟 |
| 3 | 主报告的第一部分（概念界定） | 10 分钟 |
| 4 | 本文档 §0.1 目标 + §2 里程碑 | 5 分钟 |
| 5 | 最近一条 ADR | 2 分钟 |
| 6 | 按 §6.6 的复现路径跑一次 doctor | 5 分钟 |

**Issue 与知识沉淀的衔接**：所有研究性发现先进 GitHub Issues（triage 五标签 → 判定是否需要落到文档），不直接在文档里长段落。文档只收「已经定下来的结论」，讨论留在 Issue 里。
